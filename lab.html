Start here: how the challenge lab works

This lab is a small incident simulator. You investigate a reported problem, choose a repair, test it, and explain the result. You can finish everything in the browser without writing code.

Choose what to practice

SaaS means Software as a Service: software used by customers over the internet. These missions cover tasks, billing, plans, and access.

CPaaS means Communications Platform as a Service: building blocks for communication. These missions use messaging, delivery, routing, and queue fixtures.

Beginner missions focus on one calculation or rule. Intermediate missions combine inputs and edge cases. Advanced missions combine access, lifecycle, or timing rules. All difficulties are available from the start.

Your mission workflow

  1. Read the incident. Identify what happened, the input that triggered it, and the expected result in the evidence box.
  2. Run the initial strategy. Click Run regression checks. FAIL shows an actual result that differs from the expected result.
  3. Choose a repair. Each strategy runs a different predefined implementation against the same fixtures. Try a strategy and run the checks again. Reveal hint is available without a score penalty.
  4. Explain and verify. Fill in the diagnosis, verification, and customer reply. Use the prompts below if you are stuck.
  5. Finish. Click Finish mission & get debrief. Every check must pass and all three fields must contain text. The checklist shows what remains.
  6. Continue. Finish all three required missions to complete a difficulty and all nine to complete a track. The bonus mission is optional. You can revisit any completed mission.
Worked example: repair a delivery fee

This separate example does not complete a mission or earn XP.

Report: A customer orders three packages. The delivery fee is 2 credits per package, but checkout asks for 5 credits. Evidence: packages = 3, fee = 2, actual = 3 + 2 = 5; expected = 3 × 2 = 6.

Repair: Multiply package count by the per-package fee. Adding the inputs uses the wrong operation.

Before repair: 3 packages x 2 credits -> actual 5, expected 6 -> FAIL
After repair:  3 packages x 2 credits -> actual 6, expected 6 -> PASS
Edge case:    0 packages x 2 credits -> actual 0, expected 0 -> PASS

Diagnosis: The fee was wrong because checkout added the package count to the unit fee instead of multiplying. Multiplication charges the stated fee once for each package.

Verification: I ran a regression test with three packages at two credits and expected six credits. I checked the zero-package edge case and expected zero credits.

Customer reply: Your checkout delivery estimate was affected by a calculation error. The estimate now multiplies the package count by the fee. We will check the next estimate for the same issue.

How to write your three responses
  • Diagnosis: ?When [input] happened, [old behavior] caused [problem] because [reason]. The repair [change] produces [correct behavior].?
  • Verification: ?I tested [exact input] and expected [exact output]. I also tested [empty, zero, duplicate, unknown, or boundary input] and expected [output].? Use cases you actually ran.
  • Customer reply: ?The issue affected [feature/impact]. We changed [plain-language repair]. Next we will [specific follow-up].? In the lab this describes the simulated incident.

Completion only checks that these fields contain text; it cannot prove the explanation is correct. The coaching rubric rewards detail, causal reasoning, expected outputs, an edge case, and a clear customer update.

What the technical words mean
Fixture
A small, fixed sample of input data and its expected output.
Regression check
A repeatable check that catches a broken behavior and confirms the repair keeps working.
Edge case
An input at a limit or outside the ordinary path, such as an empty list, exact expiry time, or duplicate request.
Tenant
A customer organization. A tenant check keeps one organization's records separate from another's.
Idempotency
Repeating the same operation has the same effect as doing it once. The retry missions use request IDs to recognize repeats.
Callback
An update received after an earlier request, such as a delivery status. Updates can arrive late or repeat in these fixtures.
Quota / time to live
A quota limits usage. A time to live limits how long an item remains usable; the queue expiry mission uses an explicit expiry time.
Scores, saving, and optional coding practice

Scores award up to 50 points for checks, 15 for reasoning, 15 for verification, 15 for communication, and 5 for speed. All checks must pass to earn speed points. Taking longer never prevents completion. Your best retained score per mission counts toward XP; XP and completion are separate.

Drafts, timers, selected track/difficulty, and completions save automatically in this browser. Timers include breaks and time away. Export learning record downloads your saved course data and recent debriefs; there is currently no import button. Clearing site data or switching browser/device does not carry your progress with you.

The browser runs predefined strategy simulations. It does not execute your JavaScript or modify files. For optional coding practice, repair the named function in lab-fixes.js and run node --test tests/lab-exercises.test.cjs locally with Node 22 or newer. Those tests intentionally fail until repaired. File repairs and browser completion are separate.

All data and provider rules are simplified fixtures. No messages, payments, or customer changes are sent.
